2. DIAGNOSTIC SÉCURITÉ ET STABILITÉ
─────────────────────────────────────

2.1 Protection IDOR (Insecure Direct Object Reference)

    Statut : ✅ PROTEGÉ

    Mécanismes en place :
    • Hiérarchie des rôles : user_can_edit_user() empêche un Admin
      de modifier un Directeur. Vérifié sur utilisateurs.php (edit + toggle).
    • Auto-désactivation bloquée : un utilisateur ne peut pas se
      désactiver lui-même (vérification serveur, pas seulement UI).
    • Filtrage factures vendeur : un vendeur ne voit que ses propres
      factures (filtre utilisateur_id sur la requête SQL + vérification
      post-fetch dans facture_view.php).
    • URLs signées HMAC : les liens édition sont signés avec
      HMAC-SHA256 (generate_signed_url / verify_url_signature).
      Toute falsification d'ID ou de paramètre est rejetée.

    Ressources partagées (articles, fournisseurs, mouvements) :
    • Pas de colonne utilisateur_id (par design — ressources métier globales)
    • Accès contrôlé par exiger_role() (Directeur/Admin/Magasinier)

2.2 Protection XSS (Cross-Site Scripting)

    Statut : ✅ PROTEGÉ

    • 175+ appels à h() (htmlspecialchars) dans toutes les pages
    • Toutes les sorties utilisateur échappées : données BDD, paramètres
      GET/POST, messages flash, dates, montants
    • CSP (Content Security Policy) avec nonce par session pour scripts inline
    • Aucun echo de variable brute sans échappement

2.3 Protection CSRF (Cross-Site Request Forgery)

    Statut : ✅ PROTEGÉ

    • csrf_guard() ou csrf_validate() sur les 7 pages avec traitement POST :
      articles, fournisseurs, utilisateurs, mouvements, valider_facture,
      parametres, login
    • Tokens stockés en session, validés avec hash_equals()
    • Le login lui-même est protégé CSRF

2.4 Protection Injection SQL

    Statut : ✅ PROTEGÉ

    • 38/38 fonctions utilisent des statements préparés
    • 60 instances de prepare/execute dans db_functions.php
    • 0 concaténation SQL avec $_GET ou $_POST
    • EMULATE_PREPARES=false (vraies requêtes préparées côté serveur MySQL)

2.5 Gestion des sessions

    Statut : ✅ BON (avec amélioration possible)

    • httponly : empêche l'accès JavaScript aux cookies de session
    • samesite=Lax : protection CSRF basique par le navigateur
    • secure : activé conditionnellement quand HTTPS est détecté
    • Régénération d'ID à la connexion (login.php) : anti-fixation
    • Nonce CSP : unique par session, empêche l'injection de scripts

    Amélioration possible : régénération périodique de l'ID de session
    (pas seulement à la connexion).

2.6 En-têtes de sécurité HTTP

    X-Content-Type-Options: nosniff
    X-Frame-Options: DENY
    X-X-XSS-Protection: 1; mode=block
    Referrer-Policy: strict-origin-when-cross-origin
    Content-Security-Policy: script-src 'nonce-...' (CDN allowlisté)

2.7 Gestion des erreurs

    • Messages utilisateur génériques (pas de détail technique)
    • Détails d'erreur dans error_log() pour le debug
    • Exceptions PDO attrapées dans db_transaction() avec rollback
    • Flash messages pour le feedback utilisateur

2.8 Points d'attention mineurs

    1. SECRET_URL_KEY a un fallback hardcoded en dev
       → À remplacer par une variable d'environnement obligatoire en prod
    2. Pas de régénération périodique de la session
    3. Pas de validation de force mot de passe au-delà de 8 caractères
    4. pagination_links() n'échappe pas $base_url avec h()
       (risque minime car généré programmatiquement)
    5. Quelques <?= $variable ?> sans h() dans tableau_bord.php
       (risque minime car valeurs numériques castées depuis SQL)


3. PISTES D'ÉVOLUTIONS TECHNIQUES POSSIBLES
─────────────────────────────────────────────

3.1 Migration progressive vers l'orienté objet

    Étape 1 : Créer des classes d'entité (Article, Fournisseur, Facture, etc.)
    avec leurs propriétés et méthodes. Les fonctions db_* deviennent des
    méthodes de repository (ArticleRepository, FactureRepository, etc.).

    Étape 2 : Créer un Service Layer (InvoiceService, StockService, AuthService)
    pour encapsuler la logique métier complexe (validation facture, calculs TVA).

    Étape 3 : Introduire un Container de dépendances léger pour injecter
    PDO, Session, etc. au lieu des globals.

    Bénéfice : typage fort, autocomplétion IDE, testabilité, maintenance.

3.2 Système de template / moteur de rendu

    Option A : Simple inclusion PHP avec extraction de variables
    (patterns de layout : ob_start/ob_get_clean pour capturer le rendu).

    Option B : Intégrer un moteur léger comme Twig (via Composer)
    pour la séparation HTML/PHP, l'héritage de templates, les filtres.

    Option C : Templating maison avec des fichiers .phtml et un système
    de blocks réutilisables (header, footer, pagination, alerts).

    Bénéfice : code HTML plus propre, réutilisation du layout,
    impossible d'injecter du PHP dans les templates.

3.3 Améliorations base de données

    • Ajouter des index sur les colonnes de recherche fréquentes
      (nom article, code barre, date mouvement)
    • Implémenter le soft delete pour les fournisseurs (au lieu de DELETE)
    • Ajouter une table d'audit trail (qui a fait quoi, quand)
    • Partitionnement des mouvements de stock par date si volume important
    • Vues SQL pour les statistiques du tableau de bord

3.4 Authentification renforcée

    • Régénération périodique de l'ID de session (toutes les 30 min)
    • Authentification à deux facteurs (2FA) pour les Directeurs
    • Journalisation des actions sensibles (login, modification user,
      suppression article)
    • Politique de mots de passe plus stricte (majuscule, chiffre, spécial)
    • Verrouillage de compte après N tentatives échouées

3.5 API REST

    Développer une API JSON pour :
    • Le scan de code-barres via mobile/tablette
    • L'intégration avec des caisses enregistreuses tierces
    • L'export de données vers d'autres systèmes
    • La synchronisation multi-postes

    Routes : /api/articles, /api/mouvements, /api/factures, etc.
    Auth : token Bearer JWT ou API keys.

3.6 Tests automatisés

    • Tests unitaires PHPUnit pour les helpers et db_functions
    • Tests d'intégration pour les flux critique (vente, stock, facturation)
    • Tests de sécurité (OWASP ZAP, Burp Suite)
    • CI/CD avec GitHub Actions (syntaxe, tests, deployment)

3.7 Performance

    • Mise en cache des paramètres (déjà en place via session)
    • Mise en cache des statistiques tableau de bord (TTL 5 min)
    • Lazy loading des données (ne charger que ce qui est affiché)
    • Compression des réponses (déjà en place via .htaccess)
    • CDN pour les assets statiques Bootstrap/fonts

3.8 Déploiement et DevOps
