FINDING #1 — FAILLE XSS DANS L'API (CRITIQUE)
========================================================================
Fichier : api/index.php :552
Problème : Les réponses de l'API ne passent pas par le mécanisme de
           protection anti-XSS (la fonction h() n'est pas utilisée
           côté serveur). Les données brutes de la BDD sont renvoyées
           telles quelles via json_out(). Un attaquant pourrait
           exploiter des champs nom/code_barre stockés avec du
           JavaScript malveillant pour du stored XSS via le frontend.
Impact    : Exécution de code JavaScript dans le navigateur de
            l'utilisateur connecté.
Correctif : Dans api/index.php, nettoyer les sorties avant envoi.
------------------------------------------------------------------------
   AVANT (handle_articles_list) :
   $articles = $stmt->fetchAll();
   json_out(['data' => $articles, ...]);

   APRÈS :
   $articles = $stmt->fetchAll();
   foreach ($articles as &$a) {
       $a['nom'] = htmlspecialchars($a['nom'] ?? '', ENT_QUOTES, 'UTF-8');
       $a['code_barre'] = htmlspecialchars($a['code_barre'] ?? '', ENT_QUOTES, 'UTF-8');
       $a['sku'] = htmlspecialchars($a['sku'] ?? '', ENT_QUOTES, 'UTF-8');
       $a['emplacement'] = htmlspecialchars($a['emplacement'] ?? '', ENT_QUOTES, 'UTF-8');
   }
   unset($a);
   json_out(['data' => $articles, ...]);
------------------------------------------------------------------------

FINDING #2 — INJECTION SQL DANS db_articles_stock_value (CRITIQUE)
========================================================================
Fichier : includes/db_functions.php :258
Problème : L'argument $magasin_id est interpolé directement dans la
           chaîne SQL via "$magasin_id" au lieu d'un placeholder
           préparé. Si $magasin_id provenait d'une source non fiable,
           cela créerait une injection SQL.
Impact    : Injection SQL potententielle (contournement de la BDD).
Correctif : Utiliser un placeholder préparé.
------------------------------------------------------------------------
   AVANT :
   "SELECT COALESCE(SUM(sm.quantite * a.prix_achat), 0)
    FROM stock_magasins sm JOIN articles a ON a.id = sm.article_id
    WHERE sm.magasin_id = $magasin_id AND a.actif = 1"

   APRÈS :
   $stmt = $pdo->prepare(
       "SELECT COALESCE(SUM(sm.quantite * a.prix_achat), 0)
        FROM stock_magasins sm JOIN articles a ON a.id = sm.article_id
        WHERE sm.magasin_id = :mid AND a.actif = 1"
   );
   $stmt->execute([':mid' => $magasin_id]);
   return (float)$stmt->fetchColumn();
------------------------------------------------------------------------

FINDING #3 — DOUBLE DÉCRÉMENTATION DE STOCK DANS valider_facture (CRITIQUE)
========================================================================
Fichier : valider_facture.php :175-187
Problème : La fonction db_deduire_stock_lot() décrémente déjà
           stock_magasins EN INTERNE (ligne 1944 de db_functions.php),
           MAIS valider_facture.php effectue ENSUITE une 2e décrémentation
           manuelle sur la table articles (ligne 186-187). Cela
           crée une double déduction : une sur stock_magasins ET
           une sur articles.quantite_stock. Ces deux tables ne
           sont pas synchronisées de la même manière, ce qui
           peut causer des incohérences de stock graves.
Impact    : Stock affiché erroné, ventes impossibles, pertes financières.
Correctif : Supprimer la 2e décrémentation manuelle car
           db_deduire_stock_lot gère déjà tout.
------------------------------------------------------------------------
   SUPPRIMER ces lignes dans valider_facture.php (après ligne 184) :

   // DEBUT SUPPRESSION
   $stmt_global = $pdo->prepare("UPDATE articles SET quantite_stock = quantite_stock - ? WHERE id = ?");
   $stmt_global->execute([$l['quantite'], $l['article_id']]);
   // FIN SUPPRESSION

   NOTE : La correction est déjà annotée en commentaire dans le code
   (ligne 182-183), mais la requête n'a pas été supprimée.
------------------------------------------------------------------------

FINDING #5 — SECRET_URL_KEY FAIBLE ET EXPOSÉ (MAJEURE)
========================================================================
Fichier : config/connexion.php :26
Problème : La clé secrète HMAC est une chaîne prévisible en dur
           ('estock_hmac_changez_moi_en_prod_2024'). Utilisée pour
           signer les URL (generate_signed_url), elle pourrait être
           devinée, permettant de forger des liens légitimes.
Impact    : Falsification de liens signés, accès non autorisé aux
            pages protégées (factures, articles, utilisateurs).
Correctif :

   $secret = getenv('SECRET_URL_KEY');

       error_log('ERREUR : SECRET_URL_KEY non défini ou trop court.');
       die('Configuration de sécurité manquante.');
   }
   define('SECRET_URL_KEY', $secret);
------------------------------------------------------------------------

FINDING #6 — CSP NON COMPLÈTE — CDN NON SÉCURISÉ (MAJEURE)
========================================================================
Fichier : includes/security_headers.php :13
Problème : La directive CSP autorise 'unsafe-inline' pour les styles
           et le nonce CSP ne couvre que les scripts du dossier.
           Les CDN externes (cdn.jsdelivr.net, fonts.googleapis.com)
           ne sont pas intégrés au nonce, ce qui pourrait permettre
           l'injection de scripts via un CDN compromis.
           De plus, le CDN Bootstrap n'est pas vérifié par SRI
           (Subresource Integrity).
Impact    : Attaques de type supply-chain via CDN compromis.
Correctif :
------------------------------------------------------------------------
   header("Content-Security-Policy: default-src 'self'; "
       . "style-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net "
       . "https://fonts.googleapis.com; "
       . "font-src 'self' https://cdn.jsdelivr.net https://fonts.gstatic.com; "
       . "script-src 'self' 'nonce-{$nonce}'; "
       . "img-src 'self' data:; "
       . "connect-src 'self';");

   AJOUTER SRI dans header.php et footer.php :
   <link href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/css/bootstrap.min.css"
         rel="stylesheet"
         integrity="sha384-QWTKZyjpPEjISv5WaRU9OFeRpok6YcnS/1XESKbE5QnKkT3XCVN0A6p8lNk0nq"
         crossorigin="anonymous">
------------------------------------------------------------------------

FINDING #7 — PASSAGE DU MOT DE PASSE DANS L'URL DU TICKET (MAJEURE)
========================================================================
Fichier : facture_view.php :79
Problème : Le lien vers ticket_print.php utilise un token signé
           mais le paramètre facture_id est dans l'URL en clair.
           Si le ticket est imprimé en PDF et envoyé par email,
           l'ID de facture sera exposé dans l'historique des URLs.
           De plus, ticket_print.php ne vérifie PAS la signature
           HMAC — il accepte n'importe quel facture_id valide.
Impact    : Accès non autorisé à n'importe quel ticket de caisse.
Correctif :
------------------------------------------------------------------------
   Dans ticket_print.php, ajouter la vérification de signature :

   $token = $_GET['token'] ?? '';
   if (!verify_url_signature($factureId, $token)) {
       http_response_code(403);
       exit('Accès non autorisé.');
   }

   Dans facture_view.php, ajouter le token dans le lien :
   <a href="<?= h(generate_signed_url('ticket_print.php', $id)) ?>"
      class="btn btn-outline-dark" target="_blank">
------------------------------------------------------------------------

   Dans handle_scan() :
   if (!peut('caisse_gerer')) {

FINDING #9 — RATE LIMITING NON EFFICACE — IP SPOOFING (MOYENNE)
========================================================================
Fichier : config/connexion.php :326
Problème : Le rate limiting utilise $_SERVER['REMOTE_ADDR'] pour
           identifier les IPs. Derrière un reverse proxy (Apache/Nginx),
           cette valeur est celle du proxy, pas du client réel.
           De plus, les attaquants peuvent spoof l'en-tête
           X-Forwarded-For.
Impact    : Le rate limiting peut être contourné facilement.
Correctif :
------------------------------------------------------------------------
   // Utiliser X-Forwarded-For si disponible (reverse proxy)
   function get_client_ip(): string {
       if (!empty($_SERVER['HTTP_X_FORWARDED_FOR'])) {
           $ips = explode(',', $_SERVER['HTTP_X_FORWARDED_FOR']);
           return trim($ips[0]);
       }
       return $_SERVER['REMOTE_ADDR'] ?? '127.0.0.1';
   }

   Puis remplacer les appels à $_SERVER['REMOTE_ADDR'] par
   get_client_ip().
------------------------------------------------------------------------

FINDING #11 — LOG DU MOT DE PASSE DANS L'ERREUR DE CONNEXION (MOYENNE)
========================================================================
Fichier : login.php :41
Problème : Le message d'erreur « Identifiant ou mot de passe incorrect »
           est générique (bon), mais le log d'audit enregistre le
           login tenté (suivre_activite('ECHEC_CONNEXION', ...)).
           Si le login est le mot de passe (erreur de saisie), cela
           pourrait logger un secret.
Impact    : Fuite potentielle de secrets dans les logs.
Correctif :
------------------------------------------------------------------------
   Limiter la longueur du login logué et ne logger que les 3
   premiers caractères + masque :
   $maskedLogin = substr($login, 0, 3) . str_repeat('*', max(0, strlen($login) - 3));
   suivre_activite('ECHEC_CONNEXION', 'Tentative échouée: ' . $maskedLogin);
------------------------------------------------------------------------

FINDING #12 — FORMULAIRE PARAMETRES: ABSENCE DE VALIDATION CSRF
              INTEGREE (MOYENNE)
========================================================================
Fichier : parametres.php :75-121
Problème : La validation CSRF est faite via csrf_validate() mais
           la fonction csrf_guard() n'est PAS utilisée. Si la
           validation échoue, le code continue d'exécuter le
           traitement au lieu de rediriger immédiatement.
           La condition sur la ligne 76 teste csrf_validate() mais
           ne redirige pas si c'est false — il affiche juste
           flash_error + redirect. Cela est correct mais fragilisé
           par le fait que le code continue d'exécuter les lignes
           suivantes si csrf_validate retourne true.
Impact    : CSRF possible si le token est absent (edge case).
Correctif : Utiliser csrf_guard('parametres.php') en début de bloc.
------------------------------------------------------------------------

FINDING #15 — .HTACCESS INCOMPLÈT — PAS DE PROTECTION DES FICHIERS
              SENSIBLES (MOYENNE)
========================================================================
Fichier : .htaccess (racine)
Problème : Le fichier .htaccess ne protège pas les fichiers sensibles :
           - config/connexion.php (credentials BDD)
           - includes/db_functions.php (requêtes SQL)
           - .git/ (historique git exposé)
           - database/ (fichiers SQL)
           - vendor/ (dépendances)
Impact    : Fuite de code source et de credentials.
Correctif :
------------------------------------------------------------------------
   AJOUTER dans .htaccess :

   # Protéger les dossiers sensibles
   <DirectoryMatch "^/((?!assets/).)*$">
       Require all denied
   </DirectoryMatch>

   OU (plus simple) : interdire l'accès aux fichiers PHP directement
   sauf via le front controller. Ou ajouter :
   <FilesMatch "\.(php)$">
       Require all granted
   </FilesMatch>

   # Bloquer l'accès aux fichiers de config
   <FilesMatch "\.(sql|log|env|git)$">
       Require all denied
   </FilesMatch>

   Options -Indexes
   RedirectMatch 404 /\.git
------------------------------------------------------------------------

========================================================================
FINDING BONUS — OPTIMISATIONS RECOMMANDÉES
========================================================================

1. CACHE DES PARAMÈTRES : Le cache $_SESSION['_params'] est rechargé
   à chaque requête si vide. Utiliser un cache fichier ou APCu pour
   les serveurs multi-processus.

2. INDEX SQL : Les tables articles, factures, mouvements_stock, et
   stock_magasins gagneraient des index composites sur les colonnes
   fréquemment filtrées (ex: articles.nom, articles.code_barre,
   factures.date_facture, stock_magasins.magasin_id + article_id).

3. PAGINATION OPTIMISÉE : La fonction paginate() reconstruit le SQL
   COUNT via regex. C'est fragile — préférer une requête COUNT
   séparée ou un SQL commun.

4. COMPOSER : Le fichier .gitignore ignore composer.lock, ce qui
   est déconseillé. Ce fichier doit être versionné pour garantir
   des dépendances reproductibles.

5. API RATE LIMITING : L'API ne dispose d'aucun rate limiting en
   dehors du login. Ajouter un middleware de throttling pour
   éviter les abus (ex: 100 requêtes/minute par IP).
